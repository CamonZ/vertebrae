Run progress when the workflow is a graph

The step-trail I shipped reused the linear Pipeline bar and a step 4 of 7 caption. That's the exact "X of Y" the system already banned — StateBreakdown exists because a graph that branches and loops has no honest denominator. So the run zone has to stop measuring "how far" and start describing where the run is, where it's been, and what's still reachable.

01 · the regression

A bar can't tell the truth about a graph

A route step forks; an eval can loop back; a run may visit execute three times and never touch a branch. A flat bar collapses all of that into a fake fraction.

03 · multiple workflows

A graph of graphs

This is the heart of your question. When a task fans out, it isn't one graph — the wait node nests N child sub-workflows, each running its own graph, that fan back in to a merge. So the run-map is recursive: a parent node can expand to reveal the children's sub-graphs. The hero stays compact (fan-out dots for the immediate children — the design we already have); the run-map lets you drill in.

The honesty rule

  • Never a forward fraction. No X of N against a graph — there's no honest N when the path branches or loops.
  • Compact = trajectory. The hero shows the path walked as kind-coloured chips, loops repeated with ↺, current node live. It grows; it never claims completeness.
  • Full = run-map. The inspector overlays the run on the real topology: visited solid, current pulsing, traversed edges lit, untaken branches dimmed.
  • Composition is recursive. A fan-out is a graph of graphs — the wait node nests child sub-workflows; the hero shows fan-out dots, the run-map drills in. Each child owns its trajectory.
  • Numbers describe, never divide. step executions, loop count, attempts, per-state counts — all honest. A percentage of an unknowable whole is not.
